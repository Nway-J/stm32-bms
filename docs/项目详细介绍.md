# STM32双ECU电池监测与故障管理系统

## 简介栏内容

这是一个基于两块STM32F103的电池监测学习项目。ECU-A运行FreeRTOS，负责电压和温度采集、故障判断、状态管理、CAN发送以及故障日志；ECU-B负责接收CAN数据并在OLED上显示。项目支持通过串口CLI主动注入过压、欠压、过温、NTC开路/短路等故障，可以完整观察故障确认、蜂鸣器报警、CAN上报、恢复和Flash记录过程。仓库同时保留早期裸机版本，方便对比裸机调度和多任务架构。当前硬件未加入充放电MOS，属于监测、通信与故障管理原型，不具备物理切断电流的能力。

## 为什么做这个项目

这个项目最开始只是用STM32读取电池电压和NTC温度，再通过CAN把数据发到另一块板上显示。功能逐渐增加后，采样、故障判断、CAN、Flash日志和串口输出都挤在裸机主循环里，一旦某个操作耗时，后面的功能就会被拖慢。

后来我把ECU-A迁移到了FreeRTOS，并重新整理了模块边界。改造重点不是简单地把函数放进任务，而是弄清楚哪些数据只需要“最新值”，哪些事件必须按顺序保留，哪些操作可能阻塞，以及不同任务同时访问共享资源时应该怎样保护。

项目保留了两个版本：

| 版本 | 用途 |
|---|---|
| FreeRTOS版 | 当前主版本，用于运行、验证和继续开发 |
| 裸机版 | 保留早期实现，用来对比周期调度、任务拆分和模块演进 |

## 系统结构

整套系统由两个节点组成：

```text
电池分压、NTC
      ↓
ECU-A：采样 → 故障管理 → BMS状态机
  ↓          ↓              ↓
CAN发送   Flash故障日志   蜂鸣器报警
  ↓
CAN总线
  ↓
ECU-B：报文检查 → 数据状态 → OLED显示

USB串口 → ECU-A CLI → 状态查询、故障注入、日志维护
```

### ECU-A：电池监测节点

ECU-A运行FreeRTOS，是整个项目的核心。它负责：

- ADC和DMA采集电池电压与NTC温度；
- 把ADC原始值换算为电压、温度和数据有效性；
- 判断过压、欠压、过温、NTC异常、ADC超时和CAN异常；
- 运行BMS状态机，处理启动、待机、监测、故障和恢复；
- 周期发送CAN状态，并在故障变化时尽快上报；
- 把故障发生和恢复时的现场数据写入SPI Flash；
- 通过USART CLI查询状态、注入故障和维护日志；
- 检查关键任务心跳，决定是否喂独立看门狗。

### ECU-B：仪表节点

ECU-B目前仍使用裸机主循环，主要负责：

- 接收ECU-A发送的CAN报文；
- 检查报文CRC、Alive Counter和接收超时；
- 保存最新的电压、温度、SOC和故障状态；
- 在OLED上显示实时数据；
- 通信中断时显示CAN LOST，避免把旧数据继续当作实时数据。

## ECU-A的FreeRTOS任务

| 任务 | 周期或触发方式 | 负责什么 |
|---|---|---|
| SensorTask | 每1ms | 消费DMA采样，完成电压/温度换算并发布最新快照 |
| BmsTask | 每10ms | 运行故障管理、BMS状态机、按键和报警逻辑 |
| CanTask | 周期唤醒或任务通知 | 发送电压、温度、故障报文，故障变化时尽快发送 |
| FaultLogTask | 等待故障事件队列 | 将故障发生或恢复时的现场数据写入Flash |
| DiagnosticTask | 每1ms轮询接收 | 解析CLI命令，并输出任务栈和堆等诊断信息 |
| HealthTask | 每100ms | 检查Sensor、BMS和CAN任务是否完成工作，决定是否喂狗 |

这些任务之间没有全部使用同一种通信方式：

| 数据关系 | 使用方式 | 原因 |
|---|---|---|
| Sensor → BMS/CAN/CLI | 最新快照 | 只关心最新测量，不需要处理已经过时的每次采样 |
| BMS → FaultLog | 消息队列 | 每次故障发生和恢复都要保留，不能被后来的状态覆盖 |
| BMS → CAN | 任务通知 | 只需要通知“故障状态变了”，CAN任务再读取最新状态 |
| CLI与FaultLog → Flash | 互斥锁 | 避免读日志、擦除和写入互相打断 |
| USART中断 → CLI任务 | 环形缓冲区 | 中断只收字节，完整命令留给任务解析 |

## 故障管理是怎么工作的

故障不是检测到一次异常就立刻清除或锁死，而是有一个完整过程：

```text
正常
  ↓ 条件持续成立
等待确认
  ↓ 达到确认时间
故障确认并锁存
  ↓ 达到恢复阈值
等待恢复
  ↓ 稳定时间满足，并允许人工清除
恢复正常
```

以过压为例：电压高于4.20V后先等待500ms。如果只是瞬间干扰，电压很快恢复，不会确认故障；如果持续超过500ms，系统确认过压，进入FAULT、蜂鸣器报警、CAN上报并保存Flash记录。

恢复时使用的是4.10V，而不是4.20V。两个阈值之间的差值叫迟滞，可以避免电压在阈值附近轻微波动时不断报警和恢复。电压低于4.10V并稳定1秒后，故障进入“允许恢复”状态，此时按恢复键才能清除。

### 当前故障规则

| 故障 | 触发条件 | 确认时间 | 恢复条件 | 系统表现 |
|---|---|---:|---|---|
| 过压OV | 电压高于4.20V | 500ms | 低于4.10V并稳定1秒 | 进入FAULT、报警、CAN上报、写日志 |
| 欠压UV | 电压低于3.00V | 500ms | 高于3.10V并稳定1秒 | 进入FAULT、报警、CAN上报、写日志 |
| 过温OT | 温度高于60℃ | 500ms | 低于55℃并稳定1秒 | 进入FAULT、报警、CAN上报、写日志 |
| NTC开路 | 采样被分类为开路 | 500ms | NTC恢复正常并稳定1秒 | 进入FAULT并记录传感器异常 |
| NTC短路 | 采样被分类为短路 | 500ms | NTC恢复正常并稳定1秒 | 进入FAULT并记录传感器异常 |
| 数据异常 | 传感器快照不一致 | 100ms | 数据恢复并稳定1秒 | 进入FAULT，避免使用不可信数据 |
| ADC超时 | 没有新数据或数据过期 | 立即 | 新鲜采样恢复并稳定1秒 | 进入FAULT |
| CAN降级 | 错误计数升高但未Bus-Off | 500ms | 通信恢复并稳定1秒 | 作为通信警告，不单独强制进入FAULT |
| CAN Bus-Off | 控制器进入Bus-Off | 立即 | 控制器恢复并稳定1秒 | 关键故障，进入FAULT |

多个故障可以同时存在。清除一个故障不代表其他故障也已恢复，恢复按键也不是“强制取消报警”。

## CLI串口诊断

ECU-A提供了一个简单的串口命令行，串口参数为115200、8N1。输入一条命令并发送真实的回车或换行，就能查看系统状态或进行测试。

| 命令 | 作用 |
|---|---|
| `help` | 显示支持的命令 |
| `status` | 查看BMS状态、ADC、电压、温度和采样时间 |
| `fault` | 查看活动故障、锁存故障、关键故障和恢复就绪状态 |
| `can stats` | 查看CAN发送成功、失败、Bus-Off和恢复次数 |
| `log` | 读取Flash中的启动、故障和恢复记录 |
| `log clear` | 擦除故障日志 |
| `fault inject <name>` | 注入指定故障条件 |
| `fault inject none` | 停止故障注入 |
| `watchdog test` | 主动停止喂狗，验证硬件看门狗复位 |
| `reboot` | 软件复位 |

USART接收最初使用任务轮询，任务忙或调度不及时就可能漏掉字符。现在改成USART RX中断及时读取数据寄存器，把字节写入环形缓冲区，再由DiagnosticTask解析完整命令。中断中不执行`printf`、Flash操作和命令处理，避免中断占用时间过长。

## 故障注入

故障注入是这个项目比较方便的测试入口。它不会修改ADC寄存器，也不会把真实电压强行改成某个数值，而是在故障判断入口模拟“触发条件成立”。因此可以在安全电压下重复检查后面的整条链路：

```text
CLI命令
  ↓
设置注入条件
  ↓
正常的确认时间和锁存逻辑
  ↓
BMS进入FAULT
  ↓
蜂鸣器 + CAN上报 + OLED显示 + Flash日志
```

| 注入命令 | 模拟内容 | 说明 |
|---|---|---|
| `fault inject ov` | 过压 | 不需要真的把电池升到4.20V以上 |
| `fault inject uv` | 欠压 | 可以检查欠压确认和恢复流程 |
| `fault inject ot` | 过温 | 不需要真的把NTC加热到60℃ |
| `fault inject ntc_open` | NTC开路 | 不需要实际拔掉NTC |
| `fault inject ntc_short` | NTC短路 | 不需要实际短接采样点 |
| `fault inject sensor_data` | 传感器数据异常 | 检查不可信数据处理链路 |
| `fault inject adc_timeout` | ADC数据超时 | 检查数据过期故障路径 |
| `fault inject none` | 取消注入 | 不会绕过正常恢复条件 |

### 一次完整的过压注入实验

1. 保持真实电池电压约3.9V，按启动键进入监测。
2. 发送`status`，确认电压和温度正常。
3. 发送`fault inject ov`，等待约1秒。
4. 蜂鸣器响起，ECU-B显示过压故障；发送`fault`可以看到过压已确认。
5. 发送`status`，真实电压仍然约为3.9V，说明注入没有篡改测量值。
6. 发送`log`，可以看到一条来源为INJECTED的CONFIRMED记录。
7. 保持注入时按恢复键，故障不会被强制清除。
8. 发送`fault inject none`，等待恢复条件满足，再按恢复键。
9. 故障清除，并在Flash中增加一条CLEARED记录。

这种方法验证的是“故障判断之后”的软件链路。它不能代替真实的ADC断线、NTC短路、CAN物理层干扰和高低温测试，这一点在使用时需要区分。

## CAN通信

ECU-A主要发送三种状态帧：

| 报文 | 内容 | 周期 |
|---|---|---:|
| 0x301 | 单体电压、SOC和BMS状态 | 100ms |
| 0x302 | 温度和温度有效标志 | 500ms |
| 0x303 | 故障位掩码 | 100ms，故障变化时尽快发送 |

报文中加入Alive Counter和CRC8。Alive Counter用于判断接收的是不是持续更新的新报文；CRC8用于检查数据在传输或存储过程中是否发生位错误。ECU-B还会检查接收超时，超时后显示CAN LOST，不继续把旧数据当成实时状态。

## Flash故障日志

每条日志固定32字节，保存：

- 故障发生或恢复的时间；
- 本次变化的故障和当前全部活动故障；
- 当时的电压、温度和SOC；
- BMS状态、CAN状态和复位原因；
- 数据有效标志和记录校验。

故障事件通过队列按值复制给FaultLogTask。这样后续采样继续变化时，已经入队的记录仍保留故障发生那一刻的数据。Flash写入较慢，但不会阻塞BMS故障判断任务；队列满时会增加丢弃计数，保护逻辑仍继续运行。

## 当前范围和后续计划

当前项目是单节电池的监测、通信和故障管理原型，SOC使用电压做简化估算。硬件暂时没有电流采样、均衡电路以及充放电MOS，所以FAULT只能报警、上报和记录，不能真正切断充放电电流。

后续增加充放电MOS时，计划把软件继续分成三层：故障管理只说明发生了什么；保护策略根据故障决定是否允许充电和放电；独立的MOS输出层通过专用栅极驱动器控制功率器件。过压禁止充电、欠压禁止放电，过温和传感器失效通常关闭两路。上电和复位期间输出默认关闭，恢复时继续使用迟滞和稳定时间。

这套工程主要用于学习STM32外设、CAN通信、FreeRTOS任务设计、任务间通信、故障生命周期、Flash日志和串口诊断。它已经完成当前实验板上的功能验证，但没有经过全温区、长期压力、EMC或车规安全认证，不能直接用于实际车辆或大功率电池保护。
