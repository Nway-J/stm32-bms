# 架构与数据流

## 从裸机到任务

裸机中，主循环按时间检查各项工作是否到期，一项工作耗时会拖延后续工作。主线将采样、保护判断、CAN、日志和诊断分开，允许高优先级核心工作抢占较慢的日志/诊断任务。硬件中断优先级和任务优先级是两套机制，不能直接比较数字。

| 任务 | 优先级 | 触发方式 | 栈（32位word） | 完成什么 |
|---|---:|---|---:|---|
| Health | 5 | 启动150ms后，每100ms | 192 | 检查关键任务完成心跳，决定喂狗 |
| Sensor | 4 | 每1ms | 256 | 消费DMA新数据，换算、发布快照 |
| BMS | 3 | 每10ms | 256 | 故障生命周期、状态机、按键与报警 |
| CAN | 2 | 周期到期或任务通知 | 192 | 电压/故障100ms、温度500ms，故障变化尽快上报 |
| FaultLog | 1 | 故障事件队列非空 | 192 | 写Flash、回读校验与诊断输出 |
| Diagnostic | 1 | 每1ms尝试执行 | 256 | CLI命令与每秒栈/堆统计 |

入口均在 [`app_rtos.c`](../ECU-A/App/app_rtos.c)。周期表示调度目标，不保证执行时间为零，也不能代替最坏响应时间测量。CLI一次最多取16字符，但 `log` 等命令本身可能长时间输出。优先级只决定就绪任务竞争CPU的顺序，不保证几个任务每次都严格流水执行。

## 模块地图

| 文件 | 输入 → 输出 | 职责边界 |
|---|---|---|
| `Bsp/bsp_adc_dma.c` | ADC转换 → 两路原始值 | 硬件采集，Sensor独占消费接口 |
| `App/app_sensor.c` | 原始值 → 电压/温度/有效性/序号/时间 | 不判断是否进入FAULT |
| `App/app_fault_manager.c` | 测量与条件 → 故障快照 | 确认、迟滞、恢复、锁存，不操作外设 |
| `App/app_bms_state.c` | 故障结果和按键 → 系统状态、报警 | 组织业务动作 |
| `App/app_event.c` | 状态事件 → 状态转换 | BMS内部事件，与跨任务日志队列不同 |
| `App/app_fault_event.c` | 故障边沿 → 固定事件副本 | 将故障发生时的数值保存下来 |
| `App/app_flash_log.c` | 事件 → 固定32字节记录 | 扫描、写入、校验、读取、擦除及内部互斥 |
| `App/app_can_service.c` | 最新业务数据 → CAN报文 | 单位转换、组包、计数器与发送调用 |
| `Bsp/can_protocol.h` | 字段 → 8字节负载 | 两端协议格式与CRC |
| `App/app_cli.c` | 完整命令行 → 查询/维护操作 | 不在串口中断内执行命令 |
| `Bsp/bsp_usart.c` | 接收中断 → 环形缓冲 | 中断快速取字符，任务稍后解析 |
| `App/app_health_monitor.c` | 三个心跳位 → 喂狗决定 | 工作完成后才报心跳 |
| `ECU-B/App/app_dash.c` | CAN帧 → 仪表数据与故障提示 | 校验、超时、显示；主循环100ms刷新OLED |

表中未加节点前缀的文件位于 ECU-A。驱动GPIO、蜂鸣器、SPI、TIM分别负责具体外设操作，应用层通过接口调用。

## 为什么选择不同的数据传递方法

| 关系 | 方法 | 为什么 |
|---|---|---|
| Sensor → BMS/CAN/CLI | 最新快照＋短临界区复制 | 需要完整最新测量，不需要排队处理旧采样 |
| BMS → FaultLog | 8条容量静态队列，按值复制 | 每次确认/清除需要按发生顺序保留；写Flash慢 |
| BMS → CAN | 任务通知 | 通知“状态变了”，数据由CAN再读取；允许合并为最新状态 |
| FaultLog 与 CLI → Flash | 静态Mutex | 避免读取、擦除、写入互相打断 |
| Sensor/BMS/CAN → Health | 位掩码＋短临界区 | 同一个窗口内确认三项都完成过工作 |
| USART中断 → CLI | 64字节环形缓冲 | 单生产者/单消费者，先收字符再解析；实际可用63字节 |

队列入队不等待：满了就增加丢弃计数，保护流程继续。它是有限缓冲，不承诺永不丢日志。CAN通知不保存每一个中间故障状态，事件历史由日志队列承担。

## 3.9V的一次旅行

10k/20k分压让PA0约为2.6V。ADC转换得到原始数，DMA搬入RAM。Sensor按参考电压换算，再乘1.5还原约3.9V，将本次时间和序号一起发布。BMS复制快照，检查新鲜度及故障条件。CAN任务另外复制最新测量，以mV编码；ECU-B检查CRC、Alive与时效后显示。

若变成4.3V，BMS先开始过压确认计时；持续超过500ms才确认。确认时保存的事件副本不会随之后电压变化而改变，所以日志能回答“故障发生时测到了多少”。

## 健康监控的含义

Sensor仅在发布新采样后报告心跳；BMS完成状态和事件处理后报告；CAN完成周期发送路径后报告。CAN心跳证明路径返回，**不等于总线发送成功**，发送错误另由CAN诊断管理。

Health每100ms取得并清空窗口心跳，三项齐全才喂狗。单个窗口缺失增加统计；后续恢复可以继续喂狗，持续约看门狗超时时间无成功喂狗才复位。约4秒为当前配置目标，LSI偏差会影响实际时间。
