## 怎么介绍故障注入

“我给诊断串口增加了故障注入入口。它不修改实际测量值，而是在故障判断入口强制一种异常条件，这样不用真的把电池加热或过充，就能重复检查故障确认、报警、通信和掉电记录。撤销注入也不会直接清故障，仍要满足恢复条件和人工确认，所以可以测试恢复逻辑有没有被绕过。”

| 面试追问 | 回答要点 |
|---|---|
| 为什么不直接改故障标志？ | 会跳过确认时间和生命周期，无法验证业务判断 |
| 是否验证了真实ADC断线？ | 没有；软件注入验证其后的链路，真实输入还要做硬件测试 |
| 队列满怎么办？ | 非阻塞入队失败并计数，核心判断继续；容量与消费能力需验证 |
| 为什么CAN用通知，日志用队列？ | 最新状态可以合并，但历史故障事件需要独立副本和顺序 |
| 为什么不用一个高优先级任务完成所有工作？ | Flash/串口耗时会拖延采样和判断；分离后核心可以抢占 |
| CAN心跳正常代表发送成功吗？ | 只代表路径完成；发送成败另有计数和故障诊断 |
| 看门狗是否检测所有任务？ | 当前检查采样、BMS、CAN，不检查日志和诊断任务 |
| 串口丢字节如何排查？ | 区分乱码、硬件错误、缓冲溢出和轮询不及时；本项目改为RX中断及时读DR、环形缓冲、任务解析，仍要观察错误计数 |

不要声称具有充放电硬件切断、精确SOC、AUTOSAR完整E2E或车规认证。本项目能说明的是模块边界、并发处理、诊断与可重复验证。

## 当前改进空间

- USART TX同步输出可能交错；RX缓冲也不支持无限连续输入。
- Flash底层等待的超时和错误传播需完善；日志/CLI不是当前看门狗必需心跳源。
- CAN温度负值编码尚未完善；应用CRC不覆盖ID。
- 当前主线还保留少量旧注释和未编译的历史Scheduler文件，实际任务入口以工程文件和Map为准。
- 20KB RAM下继续加任务前应测量栈和堆，不能把当前高水位当作理论上限。
